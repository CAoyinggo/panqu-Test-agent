# Panqu 画布

先确认当前子仓库、分支、宿主和需求范围，再读适用的仓库指令及 [代码入口](references/code-map.md)。这些入口是定位线索，不是跨仓库统一契约；用当前调用链核对，不能只按名称猜实现。

涉及图片节点的模型或生成行为，同时读取可用的 `panqu-image-models`；涉及视频节点的模型或生成行为，同时读取 `panqu-video-models`。只改通用拖拽、缩放、布局，不必加载两个媒体 Skill。缺少所需 Skill 时说明缺项，不声称已经调用。

## 更新组件时关注的契约

- Nuxt/Vue Flow 的插件与 React/XYFlow 的节点是两套实现，不能套用同一注册、数据或保存协议。
- 从注册入口追踪组件 kind/type、manifest、参数面板、预览、输入输出端口和执行逻辑。确认端口 ID、类型、数量及连接限制是否改变；新增组件不能只加菜单或面板。
- 分开追踪设计数据和运行态。Nuxt 的节点、连线、视口和版本保存，与任务状态、输出及运行快照不是同一事实来源；不要把运行态回写当成设计同步。
- 参数默认值、节点大小、撤销重做、复制粘贴、删除恢复、旧画布重新打开、版本恢复和旧端口连线，按此次变更挑选回归范围。旧数据无法兼容时先明确迁移策略，不能悄悄丢弃字段或边。
- 执行前的未保存位置/参数同步、重复点击、上游输出选择、任务 ID 隔离、乱序/过期推送、重连和项目切换，是执行或协作变更的重点。保存/同步失败不能误报成模型生成失败。
- 对权限相关变化检查项目归属、只读访问及版本预览隔离；不要把另一宿主隐藏按钮的行为套到当前宿主。

## 工作与验证

开发请求才修改业务代码；审查、诊断、自测请求保持业务代码只读。先从需求确定预期，再用代码确定实际入口和影响，不把现有实现当成产品规则。新增组件需标明新旧数据、支持端口和依赖媒体能力的变化。

测试时先列出“原始要求 → 涉及组件/调用链 → 检查与证据”，保留未知规则和未覆盖项。已有纯函数测试、组件/浏览器行为、真实 API 证据各自说明边界：源码正则检查不是交互验证，离线通过不是整体验收。

使用 DevTest 的环境中，专项检查用于补充需求澄清和影响分析，继续遵循 `devtest` 的计划、一次确认、立即执行和真实证据门禁；不要另写 HTTP 脚本绕过内核，也不要凭 Skill 增删已确认的验收要求。没有 DevTest 时使用仓库已有验证方式并明确限制。

先检查脚本与测试依赖再运行本地验证。Panqu 的 build/deploy 可能读取生产配置、推送镜像或上传资源，不能当成普通测试命令。生成任务、写入画布、扣费或操作线上项目需要相应授权环境；创建这个 Skill 不代表授权这些操作。
