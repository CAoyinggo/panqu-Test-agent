# 开发自测测试用例与报告模板

> 更新：2026-08-27 ｜ 维护：AI 测试智能体

> **定位**：面向「功能开发完成 → 提测前自测」环节。输入需求文档（可选接口文档、代码库、测试环境），先形成 Actor / Resource / Flow / State / Permission / Ownership / Dependency / Risk 业务模型，再产出贴近真实业务场景的测试用例，完成初步验证，并输出一页式测试报告。
>
> - 引擎级 TestCase V2 字段与生成规则（DevTest 自动生成链路使用）：[testing/testcase-v2-schema.md](testing/testcase-v2-schema.md)，代码权威在 [`src/agents/test-design/testcase-schema.ts`](../src/agents/test-design/testcase-schema.ts)
> - 配套智能体 Prompt（给开发在 AI 编程助手中直接使用）：[prompts/dev-selftest-agent.prompt.md](prompts/dev-selftest-agent.prompt.md)
> - 本模板由人工/AI 自测使用，不预填 `PASS/FAIL`；执行结论只来自真实验证

## 1. 按需求动态选择测试维度

每条 Requirement Fact/AC 都要先判断适用性，再生成 Case。没有触发信号的维度不生成占位用例；缺规则时标记 `UNKNOWN / NEED_CONFIRMATION`。

| 触发信号 | 动态选择的维度 |
| --- | --- |
| 页面、表单、交互、展示 | UI、前后端一致性 |
| 主流程、CRUD、业务规则 | 核心功能、API、数据一致性、前后置条件 |
| required/type/format/enum/min/max | 参数校验、空值、类型、格式、边界、异常 |
| 登录、角色、owner、tenant/project | 鉴权、角色权限、用户/租户/项目隔离 |
| 状态、非法状态、删除/恢复 | 状态流转、失败恢复、回滚 |
| 创建、提交、支付、发送、任务生成 | 幂等、重复提交；需求有并发风险时再加并发 |
| DB/Task/Billing/Queue/Provider/Audit | 副作用、隐藏副作用、Cross-Case Side Effect |
| 计费/积分/资损、状态流转、幂等/重复提交、并发 | 业务规则、资损核对、幂等、并发、状态机 |
| 分辨率×时长×比例组合、modelId 存在性、素材格式/大小 | 业务级参数校验 |

正向、负向和边界应按业务风险平衡。一次相同 Actor/Input/Operation/Oracle/Evidence 能覆盖多个证明义务时合并为一个 Case，不为提高数量复制请求。

Requirement 解析还必须区分“产品规则”和“测试装配元数据”：

- `AC-xxx` 只有在行首声明（允许 Markdown 标题/列表前缀）时才建立验收条件；API、Assertion、Evidence 表格里的 AC 仅为引用，不能反向生成内容为空或逗号的 AC。
- Actor/Role/Tenant/Authentication 可作为全局执行上下文；只有契约明确 `AUTH_REQUIRED` 时，单一配置 Actor 才能继承给未另行指定身份的 AC，公开接口不得自动注入身份。
- Preconditions、Test Data、Execution Steps、Assertions、Evidence、Prepare/Cleanup、Risk、Dependencies 等章节保留为用例上下文或执行契约，不独立生成业务 Case，也不进入需求歧义。
- “返回 HTTP 201”“字段非空/存在/等于”“状态从 QUEUED 转为 COMPLETED”等明确表述应形成确定性 Expected；只有真正缺少可验证结果时才进入 `UNKNOWN / NEED_CONFIRMATION`。

### 1.1 真实业务高频陷阱（必查）

| 陷阱 | 必查用例与断言 |
| --- | --- |
| 重复提交/双击 | 同一参数重复请求只产生一个任务、只扣一次费；`IDEMPOTENCY` + 计费次数=1 |
| 并发下单 | 并发同参请求产生正确数量、扣费总额正确 |
| 计费精度 | 扣费 = 单价×时长/数量；失败/取消不扣费或正确退还 |
| 状态机非法流转 | 终态任务不能再提交/修改；非法转移返回明确错误且状态不变 |
| 空/失效素材 | 素材不存在或失效时明确报错，不创建脏任务、不扣费 |

### 1.2 数据隔离双账号矩阵

隔离用例至少准备两个账号（A 属主、B 他方），逐格断言：

| 操作 | A 访问 A | B 访问 A |
| --- | --- | --- |
| 列表/查询 | 可见 | 不可见（不泄露） |
| 详情 | 可见 | 404/403 且内容不泄露 |
| 修改/删除 | 成功 | 403 且 A 数据不变 |

未提供第二个账号时，该维度进入 `BLOCKED / NEED_CONFIRMATION`，不得默认单账号通过。

### 1.3 UI 状态与交互清单

除「入口可达、展示与接口一致」外，UI 用例必须覆盖：加载态、空态、错误态、防重复点击（提交后按钮置灰）、长列表分页/滚动加载、敏感操作二次确认。每条绑定可稳定定位的页面与元素，禁止只写「查看页面」。

## 2. TestCase V2 必填结构

| 字段 | 规则 |
| --- | --- |
| Case ID | 基于执行语义稳定生成，不使用数组下标或随机值 |
| Requirement ID | 回链 Requirement；同时保留 AC、Fact、Objective 与文档位置 |
| Test Type / Aspects | Type 是执行主类，Aspects 是动态选择的多项证明义务 |
| Priority | P0~P3，来自核心 AC、风险和业务影响 |
| Business Scenario | 结构化声明 Kind、Actors、Resource/Resource ID、Ownership/Tenant、State、Permission、Flow、业务 Dependency、Risk 与 Expected Business Outcome；每项必须保留 provenance |
| Preconditions | 同时输出人类摘要和结构化 `preconditionPlan`；required 条件必须可检查 |
| Test Data | 输入值及来源、owner、tenant/project、mutable、sensitive、cleanup hook |
| Steps | 稳定 Step ID、Channel、精确动作/HTTP 绑定、依赖、AC/Fact；`PLANNED` 不可执行 |
| Expected Result | 分开 Response、State、Side Effects，值必须可判定，禁止“功能正常” |
| Assertion / Oracle | 稳定 Assertion ID；Oracle `mode=ALL`，只组合确定性断言，不由 LLM 判 PASS/FAIL |
| Evidence Required | 稳定 ID、Channel、Phase、Expectation、来源 Step、关联 Assertion/Fact |
| Cleanup | 写操作/可变数据必须声明 allowlisted Hook，并验证 cleanupStatus |
| Dependency | Environment、Contract、Identity、Test Data、Observer、Lifecycle、Case 依赖及解析状态 |
| Execution Contract | 明确 Executor、Observer、Preflight 与 Lifecycle Hook；能力仅为 `RUNTIME_REQUIRED/UNAVAILABLE` 时不得声称可执行 |
| Tags | 只用于选择和报告，不证明覆盖或执行 |
| Readiness / Execution Mode | `READY/BLOCKED/NEED_CONFIRMATION` 与 `EXECUTABLE/DESIGNED_ONLY`；无法执行不得伪装 READY |

完整字段、枚举、证据规则与场景矩阵见 [TestCase V2 权威模板](testing/testcase-v2-schema.md)。

### 2.1 Business Scenario 各结构的用途

| 结构 | 用途与 fail-close 规则 |
| --- | --- |
| `kind` | 标识核心流、状态、权限、隔离、归属、参数、幂等、并发、恢复、一致性或副作用场景；只用于驱动证明义务，不代替断言 |
| `actors[]` | 区分 `SUBJECT / OWNER / TARGET / OTHER_USER / OTHER_TENANT`；缺少越权或隔离场景所需的第二身份时进入 `NEED_CONFIRMATION` |
| `resourceContext` | 保存资源类型和可在步骤间关联的 `idRef`；资源 ID 无法捕获或预检时，组合流不得执行 |
| `ownership` | 显式表达 SELF、OTHER_USER、SAME_TENANT、CROSS_TENANT 等归属；不得把执行 Actor 自动当作资源 Owner |
| `state` | 保存已知前态、后态、禁止状态与来源；未知状态规则不得补成常见状态机 |
| `permission` | 保存 ALLOW/DENY、角色、动作和范围；未知授权结果必须是 `UNKNOWN`，不能默认 200/403 |
| `flow` | 保存单操作、顺序、并行、跨 Actor、跨租户或恢复流程，以及步骤依赖；高风险 Case 据此形成组合场景 |
| `dependencies[]` | 记录需求中识别出的业务依赖；执行能力依赖仍放在顶层 `dependencies` 与 `executionContract` |
| `risks[]` | 记录风险等级、类别、描述和来源，用于决定场景组合与优先级，不用于虚增 Case 数量 |

### 2.2 Execution Contract 与运行时回写

`executionContract` 回答四个问题：由哪个 Executor 执行、由哪些 Observer 观察、执行前检查什么、Prepare/Cleanup 如何留下证据。`AVAILABLE` 只表示能力已注册，仍必须通过 Preflight/Policy Gate；`RUNTIME_REQUIRED` 或 `UNAVAILABLE` 的 required 能力会使 Case 保持 `BLOCKED / DESIGNED_ONLY`。

运行后必须按同一个 Case/Step/Assertion/Evidence ID 将实际结果写入测试报告：Preflight 解析结果更新运行态 Readiness，真实 Evidence Artifact 回链 `evidenceRequirementId`，Oracle 只基于已采集且已验证的证据计算。设计态的 `READY` 不是 PASS；缺证据、Hook 失败、Observer 未调用或 Executor 未执行时只能是 `BLOCKED / NOT_EXECUTED / FAIL` 中符合事实的状态。

## 3. 最小结构示例

```yaml
schemaVersion: TEST_CASE_V2
id: CASE-ORDER-AC-003-CROSS-TENANT
feature: Order
name: Tenant B 用户不能修改 Tenant A 的订单
priority: P0
testType: DATA_ISOLATION
testAspects: [TENANT_ISOLATION, ROLE_PERMISSION, NEGATIVE_PATH, PRE_POST_CONDITION]
requirementStatus: CONFIRMED
source:
  requirementId: REQ-ORDER-UPDATE
  testPointId: TP-003
  acceptanceCriteriaIds: [AC-003]
  factIds: [FACT-003]
  objectiveIds: [OBJ-PERMISSION, OBJ-NON-MUTATION]
  sourceType: REQUIREMENT
  provenance: EXPLICIT
businessScenario:
  title: Cross-tenant order update denial
  goal: 阻止其他租户修改订单，避免数据越权
  actor: tenant-b-user
  action: UPDATE
  resource: ORDER
  kind: DATA_ISOLATION
  actors:
    - {id: tenant-b-user, role: USER, tenantId: tenant-b, relation: SUBJECT, provenance: CONFIGURED}
    - {id: tenant-a-user, role: USER, tenantId: tenant-a, relation: OWNER, provenance: CONFIGURED}
  resourceContext: {type: ORDER, idRef: fixture.orderA.id, provenance: EXPLICIT}
  ownership: {relation: CROSS_TENANT, ownerActorId: tenant-a-user, tenantId: tenant-a, provenance: EXPLICIT}
  state: {status: KNOWN, before: CREATED, after: CREATED, expression: denied update keeps state unchanged, provenance: EXPLICIT}
  permission: {decision: DENY, role: USER, action: UPDATE, scope: TENANT:CROSS, provenance: EXPLICIT}
  flow:
    id: FLOW-CROSS-TENANT-UPDATE
    name: Tenant B attempts to update Tenant A order
    mode: CROSS_TENANT
    steps:
      - {id: STEP-001, action: UPDATE, actorRef: tenant-b-user, resourceRef: fixture.orderA.id, operationRef: 'PATCH /orders/{id}', dependsOn: []}
  dependencies: [Tenant A order fixture]
  risks:
    - {id: RISK-CROSS-TENANT-WRITE, level: P0, category: SECURITY, description: 跨租户越权写入与数据污染, source: REQUIREMENT}
  expectedBusinessOutcome: 返回 403 且订单状态不变
  provenance: EXPLICIT
  factIds: [FACT-003]
  acceptanceCriteriaIds: [AC-003]
preconditions: [Tenant A 订单存在且归属已验证]
preconditionPlan:
  - {id: PRE-ORDER, kind: DATA, description: Tenant A 订单存在且归属已验证, required: true, checkRef: observer.order-owner}
data: {targetId: order-a-1}

  - {id: ORDER-A, source: FIXTURE, valueRef: fixture.orderA, resourceOwnerId: user-a, tenantId: tenant-a, mutable: true, cleanupHookId: CLEANUP-001}
steps:
  - {id: STEP-001, channel: API, type: HTTP_REQUEST, method: PATCH, url: /orders/{id}, description: Tenant B 更新 Tenant A 的订单, execution: PLANNED, dependsOn: [], acceptanceCriteriaIds: [AC-003], factIds: [FACT-003]}
expected:
  response: {status: 403}
  state: {expectation: UNCHANGED, description: 订单内容与归属不变}
assertions:
  - {id: AS-403, channel: RESPONSE, type: STATUS_CODE, expected: 403, factIds: [FACT-003], evidenceRequirementIds: [EV-RESPONSE]}
  - {id: AS-UNCHANGED, channel: STATE, target: orderDiff, operator: deepEquals, expected: {}, factIds: [FACT-003], evidenceRequirementIds: [EV-DIFF]}
evidenceRequirements:
  - {id: EV-RESPONSE, channel: API_RESPONSE, phase: AFTER, expectation: PRESENT, required: true, sourceStepId: STEP-001, assertionIds: [AS-403], factIds: [FACT-003]}
  - {id: EV-DIFF, channel: DATA_DIFF, phase: AFTER, expectation: UNCHANGED, required: true, sourceStepId: STEP-001, assertionIds: [AS-UNCHANGED], factIds: [FACT-003]}
oracle: {mode: ALL, deterministic: true, status: BLOCKED, assertionIds: [AS-403, AS-UNCHANGED], evidenceRequirementIds: [EV-RESPONSE, EV-DIFF]}

  - {id: CLEANUP-001, phase: CLEANUP, handler: runtime.caseCleanup, required: true}

  - {id: DEP-OBSERVER, kind: OBSERVER, ref: observer.order-snapshot, required: true, resolution: RUNTIME_REQUIRED}

  executor: {kind: COMPOSITE, ref: acceptance.scenarioRunner, status: UNAVAILABLE, supports: ['PATCH /orders/{id}', DATA_DIFF]}

    - {channel: DATA_DIFF, ref: observer.order-snapshot, phase: AFTER, required: true, status: RUNTIME_REQUIRED}
  preflight:
    - {kind: IDENTITY, ref: TENANT_B_TOKEN, required: true}
    - {kind: RESOURCE, ref: fixture.orderA.id, required: true}
    - {kind: STATE, ref: observer.order-state, required: true}
  lifecycleHooks:
    - {phase: CLEANUP, hookId: CLEANUP-001, required: true, evidenceRequired: true}
tags: [core, permission, tenant-isolation, non-mutation]
readiness: {status: BLOCKED, reasons: [COMPOSITE_EXECUTOR_UNAVAILABLE, MISSING_STATE_OBSERVER], missingCapabilities: [acceptance.scenarioRunner, observer.order-snapshot]}
executionMode: DESIGNED_ONLY
```

示例中的 Observer、Fixture、Cleanup Handler 都必须在运行环境中真实注册；任一缺失时必须保持 `BLOCKED / DESIGNED_ONLY`。当前单 HTTP Processor 尚不能消费状态断言与 `DATA_DIFF`，因此该例不能声称可执行。

组合场景必须来自业务 Flow、状态规则、权限/归属关系或风险，例如“创建 → 支付 → 重复支付”“创建 → 取消 → 再次支付”“A 创建 → B 访问”“租户 A 创建 → 租户 B 查询”“处理中 → 并发修改”“删除 → 查询 → 恢复”。每一步都要有 Actor、Resource ID 关联、`dependsOn`/并发组、Expected State/Side Effect、Oracle 和 Evidence。需求只说明单操作而未说明重复、并发或恢复语义时，可以保留风险设计，但预期必须为 `UNKNOWN` 并进入 `NEED_CONFIRMATION / DESIGNED_ONLY`，不得发明业务结果。

## 4. 初步验证规则（混合模式）

- **无接口文档时**：接口契约从代码（路由/控制器/校验中间件）或前端实际请求推导，用例中标注「推导契约」和置信度；推导预期与实测不符时先复核推导，再下 FAIL 结论。
- **静态模式**（未提供测试环境时）：对照代码实现逐条推演用例，找疑似缺陷——漏校验、越权口子、分支遗漏、实现与需求冲突；每条问题必须附证据（`文件:行号` 或需求条款原文）和置信度。
- **真实模式**（提供测试环境地址 + 账号/token 时）：按用例实际调用接口验证，记录真实请求与响应作为证据。
- **铁律**：
  1. 绝不编造执行结果；没执行的用例只能标 `NOT_EXECUTED / BLOCKED` 并写明原因。
  2. 所有会触发写操作的 400/403 负向用例都不能只看返回码，必须通过前后状态或 `DATA_DIFF` 同时确认数据未被改动、且没有隐藏副作用。只读请求可显式标记该检查不适用；5xx 则按 Requirement、Invariant 和风险决定需要哪些状态/副作用 Observer。
  3. 真实调用只打测试环境；写操作使用隔离数据并在结束后清理。
  4. 需求歧义进《待确认清单》，不得伪装成确定结论。
  5. `UNKNOWN` 必须沿链路传播：`requirementStatus=UNKNOWN/NEED_CONFIRMATION` → `oracle.status=NEED_CONFIRMATION` → `readiness.status=NEED_CONFIRMATION` → `executionMode=DESIGNED_ONLY`；后续只有权威 Requirement/Contract/配置补齐后才能解除。
  6. **存储强制**：测试用例与测试报告必须分开存放于 `/Users/mac/agents/output/{YYYY-MM-DD}/{功能名称}/测试用例.md` 和 `/Users/mac/agents/output/{YYYY-MM-DD}/{功能名称}/开发自测测试报告.md`（日期为当天，功能名取自需求，目录不存在先创建）；该文件夹只放这两个文件，需求文档原件和证据材料一律不存入。

## 5. 固定输出结构（飞书兼容 UTF-8 Markdown）

```markdown
| 最终判定 | {建议发布\|暂不发布\|待补测} | {依据} |
```

以飞书 Markdown 文件导入后的显示结果为验收标准。编号、模块、类型、结果等短字段独立保留；长字段按语义合并为`字段名：内容；字段名：内容`。通常控制在 4～6 列，确有必要时可增加。禁止使用`<br>`或任何 HTML/CSS；单元格中的管道符必须写为`\|`。空内容填写“无”或`N/A（不适用）`，不得删除章节、子模块或列。
