# 通用 Scenario 测试用例模板

> 本文说明如何编写可进入当前 Acceptance 主链的 Scenario 资产。可直接复制的唯一通用模板见 [`tests/acceptance/templates/scenario.md`](../tests/acceptance/templates/scenario.md)，风险驱动的证明义务见 [`tests/acceptance/patterns/`](../tests/acceptance/patterns/)。本文中的摘要不得替代模板字段，也不得作为第二套协议。

## 1. 基本原则

1. **设计完成不等于执行完成**。Scenario 生成、评审或通过设计质量门禁，只能说明测试已设计；只有 Runner 真实调用 Processor、完成有效断言并收齐必需证据后，才可能得到 `PASS`。
2. **一条 Scenario 只描述一个可判定业务意图**，但可以包含多个有依赖关系的 Operation。例如“创建 → 捕获资源 ID → 查询持久化状态”应写成多个显式 Step，不得把整条链路藏在一个 Processor 内。
3. **Pattern 是证明义务，不是标签装饰**。必须根据需求中的权限、隔离、状态、计费、外部依赖等结构化事实选择 Pattern，并补齐对应断言和证据。
4. Scenario 中只允许引用凭据和数据，不得保存真实 Token、Cookie、API Key 或密码。
5. 未知、缺失或歧义必须 fail-close：缺少 Processor、断言、证据、绑定、身份或范围时，不得用人工说明或报告生成成功代替真实执行。

建议资产目录：

```text
tests/acceptance/scenarios/<domain>/<scenario-id>/
├── requirement.md       # 基于 canonical Scenario 模板
├── expected.json        # Scenario Pack 必需：稳定的期望结果/基线
├── acceptance.config.example.json  # 可选：仅保留配置引用和占位符
└── server-scenario.ts   # 可选：受控本地/集成测试夹具
```

## 2. Scenario 必填结构

复制[通用 Scenario 模板](../tests/acceptance/templates/scenario.md)后，至少填写以下内容：

| 区域 | 必须回答的问题 | 约束 |
| --- | --- | --- |
| Scenario ID / Requirement / AC | 验证什么，来源是什么，何时算满足 | 每条断言必须回链到 AC |
| Priority / Patterns | 为什么优先，必须证明哪些风险 | Pattern 选择应来自结构化需求事实 |
| Actor / Role / Tenant / Project | 谁在什么范围内操作谁的资源 | 权限/隔离场景必须明确 subject、target、owner |
| Authentication | 使用哪类认证 | 只写 credential reference，不写 Secret |
| Preconditions / Test Data | 执行前什么必须成立，数据属于谁 | 每项前置条件应可检查；数据应可清理 |
| Operations | Runner 实际调用哪些 Processor/Tool | 每个 Step 唯一、可绑定、可追踪 |
| Assertions | 对响应、状态、副作用分别如何判定 | 不允许零断言或仅自然语言预期 |
| Evidence | 用什么观察结果支撑断言 | `requiredForPass` 的证据缺一不可 |
| Prepare / Cleanup | 如何创建隔离数据并恢复环境 | 只引用 allowlist hook；不得嵌入任意脚本 |
| Execution Mode / Blocked Reason | 当前是否具备安全执行条件 | 设计态只能使用下节三种值 |
| Risk / Dependencies | 有哪些副作用、成本和外部依赖 | 不确定项必须显式记录，不能默认放行 |

## 3. 设计态与运行结果

### 3.1 设计阶段允许的 Execution Mode

| 值 | 含义 | 是否可以进入执行 |
| --- | --- | --- |
| `EXECUTABLE` | Operation、Processor、断言、证据、数据与策略条件完整 | 通过 Scenario Gate 和 Policy Gate 后可以 |
| `DESIGNED_ONLY` | 测试设计已形成，但当前缺少真实执行能力或环境 | 不可以；不得产生 `PASS` / `FAIL` |
| `BLOCKED` | 已知约束明确阻断执行 | 不可以；必须提供 typed Blocked Reason |

作者不得在 Scenario 资产中预填 `PASS`、`FAIL`、`NOT_EXECUTED`、`TIMEOUT` 或 `CANCELLED`。后三种是运行实例事实，不是设计结论。

### 3.2 运行结果六态

| 状态 | 严格定义 |
| --- | --- |
| `PASS` | `executed=true`、`processorInvoked=true`、至少 1 个有效断言、全部有效断言通过，且所有 required evidence 完整并已验证 |
| `FAIL` | 已真实执行且至少一个有效断言失败；或真实业务结果与明确 oracle 不一致 |
| `BLOCKED` | Scenario Gate、Policy Gate 或执行前依赖阻断，未进行被测操作 |
| `NOT_EXECUTED` | 本次运行未完成实际被测操作，例如无 Processor、Processor 未调用、执行入口未接通或被旁路 |
| `TIMEOUT` | 已启动的执行在时限内未完成且底层任务已被取消/终止；不能转成 `FAIL` 或 `PASS` |
| `CANCELLED` | 执行被用户、系统或上游显式取消；不能转成 `PASS` |

`PASS` 必须满足以下完整谓词：

```text
executed = true
AND processorInvoked = true
AND assertions >= 1
AND passedAssertions = assertions
AND failedAssertions = 0
AND all(required evidence).present = true
AND all(required evidence).verified = true
```

因此，以下情况一律不能 `PASS`：未绑定/未调用 Processor、`executed=false`、零断言、仅检查 HTTP 2xx、缺失执行后状态、缺失必需证据、人工待办未回填、超时、取消或被策略阻断。

## 4. Pattern 选择与证明义务

Pattern 清单和详细模板以 [`tests/acceptance/patterns/`](../tests/acceptance/patterns/) 为准。常用选择关系如下：

| 结构化需求事实 | 建议 Pattern | 最小证明义务 |
| --- | --- | --- |
| 有 API Method/Path/响应契约 | `API_CONTRACT` | 精确 operation binding + 响应契约 |
| 写入或更新资源 | `PERSISTENCE` | 写响应 + 独立读回的 after-state |
| 拒绝、校验失败或禁止操作 | `NON_MUTATION` | before-state + 拒绝响应 + after-state 不变 |
| 重复提交、重试或回调 | `IDEMPOTENCY` / `CALLBACK` | 实体数和副作用次数不增加 |
| 角色、权限、资源归属 | `AUTHORIZATION` | 明确 Actor/Action/Resource + 允许/拒绝结果 |
| tenant/project 边界 | `TENANT_ISOLATION` / `PROJECT_ISOLATION` | scope 明确 + 无访问、无污染、无信息泄露 |
| 多项写入必须同成同败 | `ATOMICITY` | 所有参与项 before/after + 失败回滚 |
| 状态迁移或异步终态 | `STATE_MACHINE` / `ASYNC` | 前态、相关 ID、允许的终态与非法转换 |
| 扣费、退款、余额变化 | `BILLING` | 余额 before/after + 流水 + 精确次数 |
| 第三方调用、超时、5xx | `PROVIDER_FAILURE` | Provider 调用证据 + 本地状态 + 无重复副作用 |
| 边界、格式、长度、枚举 | `BOUNDARY` | 约束来源 + 有效/无效向量 + 确定性响应 |
| 审计或安全约束 | `AUDIT` / `SECURITY` | 关联审计证据 + 无越权/无敏感泄露 |

一个 Scenario 可以选择多个 Pattern；每个被选择 Pattern 的 required proof obligation 都必须映射到断言与证据，不能只把 Pattern 名称写进列表。

## 5. Operation Binding 规范

每个 Operation 使用唯一 Step ID，并至少声明 `Channel`、`Processor`、AC 引用和 Evidence 引用。Channel 支持 `API`、`UI`、`DATA`、`QUEUE`、`PROVIDER`。

API Operation 还必须精确声明 `Method + Path`：

| Step | Channel | Processor | Method | Path | Request | Capture | AC | Evidence |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `STEP-001` | API | api | POST | `/api/resources` | `{"name":"${RESOURCE_NAME}"}` | `resourceId=body.data.id` | AC-001 | EV-001 |
| `STEP-002` | API | api | GET | `/api/resources/${STEP-001.resourceId}` | - | `persistedName=body.data.name` | AC-001 | EV-002 |

多 API 链路必须遵守：

- 一个 Step 只对应一个可审计的 Operation；不得只写“调用相关接口”。
- 后续 Step 使用前序 `Capture` 的命名输出，不依赖隐式全局变量。
- 每个 Step 都绑定至少一个 AC；每个决定结果的 AC 都有断言与 required evidence。
- Processor 必须显式支持 Channel/Operation；名称存在但未调用仍视为 `NOT_EXECUTED`。
- 绑定缺失或 Method/Path 歧义必须在 Scenario Gate 阻断，不得在 Prepare 后才发现。

## 6. 响应、状态与副作用

不要只验证响应文本。根据业务语义分别定义：

- **Expected Response**：状态码、错误码、响应 schema 和关键字段。
- **Expected State**：执行前状态、执行后状态、允许的状态迁移和持久化读回。
- **Expected Side Effects**：必须发生、禁止发生以及精确次数，例如账单、事件、通知、Provider 调用和审计记录。

成功写操作至少需要响应断言和独立的 after-state 证据。拒绝或失败操作至少需要拒绝响应以及 Non-Mutation 证明：保存 before-state，执行操作，再通过独立观察通道证明 after-state 未改变且没有禁止副作用。

## 7. Assertion 与 Evidence 规范

断言必须结构化声明 `channel + target + operator + expected/expectedFrom`，并引用 Operation、AC 和 Evidence Requirement。允许的通道包括响应、状态、数据、副作用、审计和系统观测；自然语言“结果正确”不是有效断言。

证据必须说明：

- 来源 Step/探针与采集时间；
- 覆盖哪些 AC 和断言；
- 是否 `requiredForPass`；
- 是否完成校验和脱敏；
- 对状态、账单、事件等，是否使用与操作独立的观察通道。

截图、日志或 HTML 报告本身不自动等于业务证据。只有与本次 run、operation、assertion 关联且可验证的 Evidence Envelope 才能参与 `PASS` 判定。

## 8. Prepare / Cleanup 规范

Scenario Gate 和 Policy Gate 必须在任何 Prepare 或真实副作用之前执行。推荐顺序：

```text
Scenario Parse → Pattern/Proof Validation → Scenario Gate → Policy Gate
→ Prepare → Operation(s) → Assertions/Evidence → Outcome → Cleanup
```

- Prepare/Cleanup 只引用 Runner allowlist 中的 hook handler，Markdown 不得携带可执行代码。
- Prepare 创建的数据必须绑定本次 Actor/Tenant/Project 和 run ID，并通过同一个 execution context 传入 Operations。
- 可变数据应声明 owner、是否敏感以及对应 cleanup hook。
- Cleanup 放在 `finally` 语义中执行；Cleanup 失败必须单独报告，不能覆盖原执行结果，也不能伪造 `PASS`。
- `BLOCKED` / `DESIGNED_ONLY` 场景不得先 Prepare 再判断可执行性。

## 9. Blocked Reason

阻断必须使用结构化原因：`code + stage + message + details + recoverable`。例如：

```yaml
code: MISSING_OPERATION_BINDING
stage: GATE
message: STEP-002 缺少唯一 Method + Path 绑定
details:
  operationId: STEP-002
recoverable: true
```

禁止仅用“执行失败”“待人工”或错误字符串前缀代替可统计的阻断原因。

## 10. LEGACY 资产说明

历史 `tasks/*.json`、旧式单行用例表和 TypeScript 中的内嵌 Markdown 仅作为 **LEGACY** 输入或参考材料。它们只有在显式转换并通过 canonical Scenario Gate 后，才可进入新执行链；其存在不代表迁移已经完成。

若仍需维护旧清单，可保留 `编号 / 优先级 / 分类 / 用例名称 / 前置条件 / 步骤 / 预期结果` 作为需求盘点视图，但：

- “API / 浏览器 / SQL”只表示期望通道，不证明 Processor 已接入；
- “待人工”不是运行结果状态，应映射为 `DESIGNED_ONLY` 或 `NOT_EXECUTED`；
- 旧表不得手工填写 `PASS`，也不得作为自动化结果来源；
- 新增或修改场景应优先落到 canonical Scenario 目录，不再扩展第二套模板。
