# 开发交接、发布与报告输出检查清单

本清单是开发交接、发布以及测试报告输出的强制门槛。以下规则适用于今后所有**开发自测报告**和**测试报告**；任何强制项未满足时，不得将报告标记为“验收通过”或“建议发布”，也不得省略不符合项。

## 1. 标准报告输出格式（强制）

### 1.1 文件规范

- [ ] 使用 UTF-8 Markdown（`.md`）。
- [ ] 所有输出文件必须写入 `/Users/mac/agents/output/{YYYY-MM-DD}/{功能名称}/`，禁止写入代码库、`test-flow` 或其他目录。
- [ ] `{YYYY-MM-DD}`使用报告输出时的 Asia/Shanghai 日期；`{功能名称}`使用可识别的需求或功能名称，且不得包含路径分隔符。
- [ ] 每个功能输出目录必须同时包含以下两个固定文件，缺一不可：

```text
/Users/mac/agents/output/{YYYY-MM-DD}/{功能名称}/
├── 测试用例.md
└── 开发自测测试报告.md
```

- [ ] `测试用例.md`必须包含本次生成的全部测试用例及其执行状态、Oracle 和证据/备注。
- [ ] `开发自测测试报告.md`是最终报告的固定文件名；文件名中的“开发自测测试报告”是输出约定，不替代报告正文中的“报告类型”。
- [ ] 报告正文中的`报告类型`只能是“开发自测报告”或“测试报告”。
- [ ] 报告不得包含 Cookie、JWT、应用密钥、个人凭证或其他明文敏感信息。

### 1.2 固定章节及顺序

以下章节必须全部保留，顺序不得调整；没有内容时填写“无”或 `N/A（不适用）`，不得删除章节。

1. `结论概览`
2. `需求与实现核对`
3. `用例执行清单`
4. `审查中发现的问题`
5. `自动化执行证据`
6. `未覆盖项与回归建议`
7. `发布判定`

报告标题和元信息必须包含：

- [ ] 需求名称、需求文档或来源
- [ ] 报告类型
- [ ] 测试人、日期和时区
- [ ] 代码库、分支/基线及未提交改动说明
- [ ] 测试环境
- [ ] 验证模式或测试范围
- [ ] 安全与计费操作说明

### 1.3 结论概览

`结论概览`必须分别输出以下内容，不得用一个笼统的“通过”替代：

- [ ] 用例统计：总数、`PASS`、`FAIL`、`BLOCKED`、`NOT_EXECUTED`
- [ ] 代码级结论：仅说明代码审查、静态检查、构建或单元测试覆盖层级
- [ ] 环境级结论：说明真实环境 UI、API、数据、任务及外部依赖的验收状态
- [ ] 发布判定：明确“建议发布”“暂不发布”或“待补测”，并给出依据
- [ ] 主要边界、风险和覆盖情况

代码级 `PASS` 不得被描述为测试环境或业务验收通过。

### 1.4 用例状态（唯一允许值）

用例明细的结果字段只允许使用以下四种状态：

| 状态 | 强制定义 |
|---|---|
| `PASS` | 对应测试层级已经真实执行，Oracle 满足，且报告中存在可核对的证据 |
| `FAIL` | 已执行，但实际结果不符合需求、Oracle 或验收标准 |
| `BLOCKED` | 已尝试执行，但被环境、权限、依赖、数据或工具问题阻断 |
| `NOT_EXECUTED` | 尚未执行；不得以静态推断、历史结果或计划代替执行结果 |

- [ ] 每条用例必须包含编号、模块、测试点/场景、类型、结果和证据/备注。
- [ ] 静态审查、构建和运行时验收必须标明各自测试层级；某一层级的 `PASS` 不得外推到其他层级。
- [ ] 内部系统产生的 `WARNING`、`KNOWN_ISSUE`、`FLAKY` 等状态不得直接写入用例结果列；必须按本节定义归入四种标准状态，并在备注中保留原始信息。
- [ ] `PASS` 必须有证据；`FAIL` 必须写明实际结果和影响；`BLOCKED` 必须写明阻断原因及解除条件；`NOT_EXECUTED` 必须写明补测条件。

### 1.5 缺陷状态（唯一允许值）

审查或测试发现的问题只允许使用以下三种状态：

| 状态 | 强制定义 |
|---|---|
| `OPEN` | 尚未修复，或修复尚未完成 |
| `RESOLVED（待验证）` | 开发已经修改代码，但尚未完成目标环境回归验证 |
| `VERIFIED（验证通过）` | 修复已在要求的环境和范围内完成回归验证，并有证据 |

- [ ] 全程禁止使用 `CLOSED`。
- [ ] “开发已修复”只能标记为 `RESOLVED（待验证）`，不得写成“验收通过”。
- [ ] 每条问题必须包含编号、级别、问题描述、状态、修复说明或验证证据。

### 1.6 统计一致性（输出前强制校验）

必须满足以下等式：

```text
用例总数 = PASS + FAIL + BLOCKED + NOT_EXECUTED
```

- [ ] 统计值与用例明细逐项计数一致。
- [ ] 自动化执行证据中的状态与用例清单一致。
- [ ] 缺陷汇总数量与问题明细一致。
- [ ] `测试用例.md`与`开发自测测试报告.md`中的用例编号、状态和统计完全一致。
- [ ] 任何一项不一致时，必须先修正，禁止输出报告。

### 1.7 发布判定规则（强制）

只有同时满足以下条件，才能输出“验收通过”或“建议发布”：

- [ ] 全部必测项已执行并通过，即必测项 `FAIL = 0`、`BLOCKED = 0`、`NOT_EXECUTED = 0`。
- [ ] 不存在 `OPEN` 或 `RESOLVED（待验证）` 的发布阻断问题；要求验证的问题均为 `VERIFIED（验证通过）`。
- [ ] 代码级结论与环境级结论均有独立证据。
- [ ] 回归、计费、数据污染、安全和外部依赖风险已验证或明确判定为 `N/A（不适用）`。

未满足上述任一条件时，发布判定必须写为“暂不发布”或“待补测”，并列明未满足项。

### 1.8 输出前最终检查

- [ ] 固定七个章节齐全，空章节已填写“无”或 `N/A（不适用）`。
- [ ] 状态值、状态含义和结论用语符合本清单。
- [ ] 总数等式校验通过。
- [ ] 所有结论均能追溯到用例、命令、日志、截图或其他有效证据。
- [ ] 报告已完成敏感信息检查。
- [ ] 输出目录、两个固定文件名和报告类型符合规范。
- [ ] 输出文件未写入代码库、`test-flow` 或其他非标准目录。

### 1.9 飞书 Markdown 表格与可读性（强制）

本节适用于 `/Users/mac/agents/output` 下所有现有及今后生成的`测试用例.md`和`开发自测测试报告.md`。产物以飞书的 Markdown 文件导入结果为验收标准；不以直接粘贴 Markdown 源码的效果为准。

- [ ] 报告正文不得出现`<style>`、`<div>`、`<table>`、`<br>`、`<code>`、`<a>`、`<strong>`等任何 HTML/CSS 标签或样式源码。
- [ ] 全部表格必须使用飞书可导入的原生 Markdown 管道表格；表头、分隔行及每条数据的列数必须完全一致。
- [ ] 编号、模块、类型、结果等短字段独立保留；相关长字段按语义合并，并在单元格中使用`字段名：内容；字段名：内容`连续展示。
- [ ] 禁止使用 HTML 换行；单元格中的换行统一改为中文分号，Markdown 表格分隔符`|`必须转义为`\|`。
- [ ] 不设置机械的列数上限，通常控制在 4～6 列；确有必要时可以增加，但必须优先保证飞书可读性和数据完整。
- [ ] 每个明确章节或业务子模块只保留一张完整表格；没有子模块的章节只保留一张总表。一个章节或子模块内禁止出现多张并列表格。
- [ ] “用例执行清单”必须把全部模块、字段和记录直接合并在一张完整表格中，`模块`作为表格列；禁止按模块、编号或“概览＋详情”拆表。
- [ ] “审查中发现的问题”必须把问题描述、复现、证据、修复/验证信息和状态直接放在一张完整表格中；禁止按问题编号或“概览＋详情”拆表。
- [ ] 价格 Oracle 必须保留为一张完整表格；需求与实现核对存在明确子模块时每个子模块各一张完整表格；待确认清单、运行时用例、关键运行步骤、覆盖情况和自动化执行证据同样不得拆成概览与详情。
- [ ] `测试用例.md`中的全部正式用例、运行时用例和关键步骤必须合并为一张完整用例表；字段只适用于部分记录时填写“无”或`N/A（不适用）`，不得另起详情表。
- [ ] 同类表格必须统一表头命名和字段顺序，不得出现多个表头合并到同一单元格或空表头占位。
- [ ] 表格与章节/子模块标题之间必须保留空行；禁止使用颜色、Emoji、HTML 实体或与数据无关的装饰内容。
- [ ] 文件必须继续使用 UTF-8 Markdown（`.md`）；链接、加粗和行内代码分别使用标准 Markdown 语法，不得使用对应 HTML 标签。
- [ ] 表格优化只允许改变展示结构和留白，不得修改测试数据、用例状态、缺陷状态、统计结果或报告结论。
- [ ] 输出前必须检查无 HTML/CSS、无`<br>`、Markdown 表格列数一致、每个章节/子模块只有一张完整表格、无“概览＋详情”，并重新执行第 1.6 节的统计一致性校验。

## 2. 开发交接与发布检查

以下清单由 `npm run acceptance:test`、`npm run test:p0`、全量测试、Agent Eval 和构建共同验证。发布前必须执行文末命令并保存结果。

- [x] Requirement 可解析
- [x] AC 可追溯
- [x] Test Point 可生成
- [x] API Case 可生成
- [x] 参数边界正常
- [x] 权限场景正常
- [x] 数据隔离正常
- [x] API 可真实执行
- [x] PASS/FAIL 正确
- [x] BLOCKED 正确
- [x] NOT_EXECUTED 正确
- [x] Defect 分类正确
- [x] 报告生成
- [x] 报告脱敏
- [x] Run 可重跑
- [x] Run 不互相污染
- [x] 报告不覆盖
- [x] video/WAN3 回归通过
- [x] P0 回归通过
- [x] Agent Eval 通过
- [x] Build 通过

```bash
npm run build
npm run acceptance:test
npm run test:p0 -- --reporter=dot
npm test -- --reporter=dot
npm run agent:eval
git diff --check
```

### 2.1 GitHub 推送前全量同步（每次必做）

只要用户提出“推送到 GitHub”“同步 GitHub”或同等要求，执行者必须先完成以下检查，不能只检查或提交用户刚点名的文件：

- [ ] 先执行远端同步检查，确认目标仓库、目标分支和远端最新提交；不得把其他仓库、旧系统或产品源码误推到当前仓库。
- [ ] 递归检查整个工作树的文件修改时间，将晚于最近提交或本轮基线的时间作为复核线索；Git 不记录文件修改时间，最终必须继续比较实际内容和内容哈希。
- [ ] 同时检查已修改、已删除、未跟踪及被忽略文件；被忽略文件也要确认是否只是依赖、缓存、构建产物、测试输出或临时文件，防止有效源码被错误忽略。
- [ ] 使用 `git status --short --untracked-files=all`、`git diff --name-status <remote>/<branch>` 和必要的逐文件哈希比较，识别文件名未变但内容已更新的文件。
- [ ] 所有属于当前仓库的有效最新源码、模板、文档、配置示例和测试必须在同一次同步中提交；不得只推点名文件而遗漏其他已更新内容。
- [ ] `.git`、真实凭证、Cookie/Token、`node_modules`、缓存、构建产物、测试输出和临时文件禁止提交；安全扫描失败时必须停止推送。
- [ ] GitHub 独有文件默认保留；未经明确授权不得因“覆盖同步”删除远端独有文件或强制改写历史。
- [ ] 提交前检查版本号、README、CHANGELOG、模板更新时间及实现/文档/测试是否一致，并运行与变更风险相匹配的类型检查和测试。
- [ ] 推送完成后再次读取远端分支哈希，确认本地 `HEAD` 与远端目标分支完全一致；`Everything up-to-date` 不能替代前述全仓内容检查。

以上任一项未执行，不得向用户报告“所有最新内容已推送”。

最后四项只能在上述交付前命令真实通过后勾选。报告输出还必须同时通过第 1 节全部强制检查。
